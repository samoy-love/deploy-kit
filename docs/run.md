# Локальный запуск: `dk run`

`dk` умеет выкатить любую цель любого проекта. Локально такого не было: чтобы
поднять проект, надо было помнить команду, каталог, порт и набор переменных —
и везде они разные. Запустить ферму целиком или поднять чужой проект на
конкретной ветке было нельзя иначе как вручную.

`dk run` — тот же реестр целей, те же имена, то же обнаружение, но на своей
машине.

```
dk run                     все сервисы проекта, в котором стоишь
dk run <цель> [<цель>…]    выборочно
dk run --all               всё, что вообще запускается локально
dk run --list              что запускается и на каких портах
dk run --dry-run           план: каталоги, порты, переменные — ничего не делая
dk run --branch main       на другой ветке, через отдельный worktree
dk run --force             занятый порт освободить, а не отказаться стартовать
```

## Почему не Docker

Вопрос возникает первым, поэтому ответ здесь, а не в конце.

* **Контейнер не был бы продом.** Прод — это `release.sh`, `releases/<версия>`,
  атомарный симлинк `current`, `install_units`, `systemctl restart`, reload
  nginx, healthcheck и откат, всё на arm64. Изоляцию там даёт systemd:
  `ProtectSystem=strict`, `MemoryDenyWriteExecute=true`,
  `SystemCallFilter=@system-service`. Локальный Docker не воспроизводит ни
  архитектуру, ни этот sandbox, ни nginx перед сервисом.
* **Это был бы третий рантайм.** Правило хозяйства — «локальная выкатка и CI
  идут одним и тем же путём». Docker не используется ни локальной выкаткой, ни
  CI, ни продом; появившись, он стал бы единственным местом, где «работает», и
  расхождение с остальными тремя было бы вопросом времени.
* **Клиент в контейнер не влезает.** ChillHub — `net8.0-windows`, WPF, WebView2,
  реестр, `%APPDATA%`, синхронизация игр на диске. Linux-WPF не существует, GUI
  в Windows-контейнере — тоже.
* **HMR деградирует.** Vite и Astro держатся на inotify; через bind-mount в
  Docker Desktop события теряются, лечится `usePolling` — постоянный CPU и
  задержка секунды вместо десятков миллисекунд.
* **Цикл правки становится длиннее.** `go run` с тёплым кешем — секунды;
  пересборка слоя — десятки, плюс память на VM до старта хоть чего-то.

Единственный настоящий довод за Docker — дрейф версий тулчейнов. Он чинится
двумя однострочными файлами на репозиторий (`.nvmrc`, `.go-version`), которые
теперь и лежат, а не миграцией.

Docker остаётся там, где уже оправдан: стек мониторинга (серверный, наблюдает
за неконтейнеризованными сервисами) и visual-QA в MetroMap (настоящий
Chromium).

## Ключи `RUN_*`

Живут в `.deploy-kit/*.env` — том же файле, что описывает выкатку. Отдельный
файл под запуск означал бы второй реестр и второй способ рассинхронизироваться:
цель появлялась бы в одном списке и пропадала из другого.

| Ключ | Смысл | Пример |
|---|---|---|
| `RUN_CMD` | команда старта. Нет ключа — цель локально не запускается | `go run ./cmd/api` |
| `RUN_DIR` | рабочий каталог относительно корня проекта | `server` |
| `RUN_PORT` | порт: по нему проверяется готовность и по нему же цель гасится | `55700` |
| `RUN_ENV` | переменные через `;`, только безопасные для локальной машины | `COOKIE_SECURE=false;PORT=%PORT%` |
| `RUN_HEALTH` | путь проверки живости на `RUN_PORT` | `/healthz` |
| `RUN_NEEDS` | цели, которые должны подняться раньше, через запятую | `chillhub-api` |
| `RUN_SECRETS` | переменные, которым раннер выдаёт эфемерное значение | `JWT_SECRET;ADMIN_PASSWORD_PLAIN` |
| `RUN_ONESHOT` | цель отрабатывает и выходит — ждать её, а не следить за ней | `1` |
| `RUN_SKIP` | причина, по которой цель локально не поднимается | `нужен Linux и systemd` |
| `RUN_NOTE` | что человеку надо знать при запуске | `пароль печатается ниже` |

`BUILD_CMD` для запуска не годится и подменой не является: у пяти Go-целей в
нём стоит `GOOS=linux GOARCH=arm64`, то есть локально он собирает бинарь под
сервер, который на машине разработчика не запустится.

Цель без `RUN_CMD` и без `RUN_SKIP` в `--list` показывается как «нет `RUN_CMD`
в описании цели» — это не «не запускается», а «не заполнено», и разница видна
только там.

### Подстановки

В `RUN_CMD` и `RUN_ENV` раскрываются четыре:

| Подстановка | Что это |
|---|---|
| `%PORT%` | значение `RUN_PORT` |
| `%DIR%` | корень дерева, из которого идёт запуск (с `--branch` — worktree) |
| `%MAIN%` | корень проекта в **основном** дереве, worktree его не меняет |
| `%KIT%` | корень deploy-kit |

На Windows пути подставляются в родном виде (`C:/…`, не `/c/…`): Go и .NET о
MSYS-путях не знают.

**Подставленный путь берите в кавычки.** Команду выполняет шелл, а в путях
хозяйства есть пробел — без кавычек аргумент разъезжается надвое, и сервис
падает на «не найден `C:/Users/Alexey`». Значение при этом удобнее писать в
одинарных кавычках, а внутренние — в двойных:

```sh
RUN_CMD='go run . -config "%DIR%/config/status.json" -data "%MAIN%/data"'
```

`%MAIN%` существует ради общего состояния. Контент лаунчера и данные агента
лежат вне git, и в свежем worktree их не будет — а прод устроен так же, там
контент лежит вне каталога релиза и выкатка его не касается.

## Порты

Порт фиксируется в `RUN_PORT` и передаётся команде явно, потому что и Vite, и
Astro при занятом порте **молча уезжают на соседний**. При запуске нескольких
сайтов разом второй оказывается не по тому адресу, который написан в ссылках,
в `.claude/launch.json` и в сквозных тестах, — и понять это можно только вычитав
лог.

| Цель | Порт |
|---|---|
| snakes | 3000 |
| samoylove | 4321 |
| status-site | 4331 |
| metro | 5173 |
| die-game | 5175 |
| chillhub-api | 55700 |
| chillhub-admin | 55777 |
| chillhub-site | 55780 |

Занятый порт — отказ, а не тихий переезд и не расстрел чужого процесса. Забрать
его силой можно явно: `--force`.

## Остановка

`Ctrl-C` гасит всё, что подняла команда, **по порту, а не по PID родителя**.
Это не перестраховка: `go run` компилирует бинарь во временный каталог и
запускает его отдельным процессом, так что порт держит внук — убийство самого
`go run` оставляет сироту, которая мешает следующему запуску. То же делает npm
со своим шеллом.

На Windows это два разных убийства, и путать их нельзя: свои процессы раннер
знает по идентификаторам MSYS и гасит `kill`, а `netstat` отдаёт
идентификаторы Windows, понятные только `taskkill`. Перепутав, можно попасть
в постороннюю программу с тем же номером.

## Ветки

`--branch` раскладывает ветку в отдельный `git worktree` и запускает из него.

* **worktree, а не `checkout`** — в рабочих деревьях лежит незакоммиченная
  работа, и `checkout` её снёс бы или потребовал stash. Без `--branch` никакой
  worktree не создаётся: работаем в текущем дереве со всеми правками, и это
  дефолт.
* **вне каталогов проектов** — в `~/.cache/deploy-kit/worktrees/<проект>/<ветка>`.
  worktree внутри репозитория ломает поиск и аудит: grep начинает находить
  вторые экземпляры конфигов.
* **`npm ci` один раз на ветку** — в свежем дереве нет `node_modules`. В
  основном дереве раннер зависимости не трогает: тихая переустановка чужого
  `node_modules` — не то, чего ждут от команды запуска.

Общее состояние (контент лаунчера, данные агента) остаётся общим через
`%MAIN%` — см. подстановки выше.

## Секреты

`RUN_SECRETS` перечисляет переменные, которым раннер выдаёт случайное значение
на запуск: оно печатается в консоль и никуда не пишется. Следующий запуск
выдаст другое.

Так поднимается админка лаунчера. До этого единственным путём был
`scripts/run-dev.ps1`, который спрашивал пароль через `Read-Host` — то есть
поднять ферму одной командой было нельзя в принципе: она останавливалась и
ждала ввода. Постоянный пароль в файле рядом с репозиторием — ровно тот
способ, которым секрет однажды уезжает в git, поэтому его здесь нет.

## Цели только для локального запуска

`LOCAL_ONLY=1` в описании цели означает, что на проде её нет вовсе: WPF-клиент
попадает к пользователю установщиком и обновляет себя сам, каталога на сервере
и юнита у него нет. `dk`, `dk list` и `dk deploy --all` такую цель не видят —
иначе статус вечно показывал бы её красной строкой «нет ответа», а выкатка
всего хозяйства пыталась бы её катить. `dk run` видит.
