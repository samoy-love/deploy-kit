# Событие выкатки

Один JSON на все пути выкатки: GitHub Actions, `dk deploy` с машины,
`server/release.sh`, `server/rollback.sh`, `server/publish-file.sh`,
`bin/install-server`. Пишет тот, кто выкатывает; читает бот статуса; в чат
говорит только бот.

Этот файл — контракт. Его читают обе стороны, и обе проверяются одними и теми
же образцами: `docs/events/example-success.json`,
`example-failure.json`, `example-rolled-back.json` лежат рядом и подключены
golden-файлами в тестах shell-генератора и Go-разбора. Правка схемы без правки
образцов — это правка, о которой узнают на проде.

## Почему событие, а не наблюдение

Сегодня о релизе узнают по разнице двух снимков `/version.json`. Разница
существует не всегда: три выкатки за минуту дают одно сообщение, выкатка с
откатом — ноль, провал выкатки — ноль (версия не менялась, сравнивать нечего),
автооткат — ноль. Событие рождается там, где происходит, и не зависит от того,
успел ли кто-нибудь заметить последствие.

Отсюда главное требование ко всему, что ниже: **потерять событие нельзя, а
показать его дважды — нельзя тем более**. Первое даёт правила журнала и
курсоров, второе — правило `id`.

---

## 1. Где лежит журнал

```
/var/lib/deploy-kit/events/
```

Каталог задаётся переменной `DK_EVENTS_DIR` (умолчание — путь выше) и обязан
существовать до первой выкатки: его заводит `bin/install-server`.

**Не `/var/www/status/data/`, где лежит `summary.json`.** Этот каталог nginx
раздаёт наружу как `/data/`
(`nginx/sites/status.samoy.love.conf`, `location /data/`), и события уехали бы
в открытый доступ целиком: адреса прогонов, стадии провалов, история неудачных
выкаток — всё, что владелец видит в чате, но чего на публичной странице быть не
должно. На страницу попадает то, что туда положит агент, а не сырой журнал.

Каталог обязан лежать на той же файловой системе, что и временный файл записи
(см. §3), — то есть `.tmp` пишется прямо в него, а не в `/tmp`.

---

## 2. Имя файла

```
<unix-ms>-<app>-<kind>.json
```

* `<unix-ms>` — момент события в миллисекундах эпохи, **ровно 13 цифр**, с
  ведущими нулями, если бы их не хватило;
* `<app>` — та же строка, что в поле `app`;
* `<kind>` — то же, что в поле `kind`.

```
1785924102123-snakes-success.json
1785925215123-metro-rolled_back.json
```

**Лексикографический порядок обязан совпадать с хронологическим**, потому что
на нём держится курсор читателя: приёмник хранит имя последнего обработанного
файла и берёт всё, что строго больше него как строка. Никакого чтения времени
из содержимого при этом не происходит — иначе курсор пришлось бы сверять с
разобранной датой, а разбор мусорного файла не должен влиять на продвижение по
журналу.

Отсюда фиксированная ширина в 13 цифр. Числа разной длины сортируются как
строки неправильно: `9999999999999` (2286 год) лексикографически больше
`10000000000000`, а `999999999999` (2001 год) — больше всего, что после него.
Тринадцати цифр хватает до 2286 года, и все они значащие уже сегодня; ведущие
нули — страховка на случай машины со сбитыми часами, а не украшение.

**Столкновение по миллисекунде.** Три выкатки в одну секунду — сценарий
приёмки, две в одну миллисекунду — редкость, но не невозможность. Писатель под
своим замком (`flock` на `<каталог>/.lock`) проверяет, свободно ли имя, и при
занятости увеличивает `<unix-ms>` на единицу, пока не освободится. Так шаблон
имени остаётся ровно таким, как здесь написано (никаких суффиксов, никакого
второго формата для читателя), а порядок остаётся строго возрастающим.
Смещение на миллисекунду вперёд не искажает ничего: настоящее время события
лежит в поле `at`, а имя — это ключ сортировки.

## 3. Атомарная запись

```
<имя>.json.tmp   → записать целиком → fsync → chmod 0640 → rename → <имя>.json
```

`rename(2)` внутри одной файловой системы атомарен: читатель видит либо старое
состояние каталога, либо файл целиком. Без этого читатель, который тикает раз в
секунду, рано или поздно откроет файл посреди записи и получит оборванный JSON.
Отбросить его — потерять событие (курсор уже прошёл мимо), не отбросить —
уронить разбор.

Двойная страховка на том же месте: читатель берёт **только** имена, подходящие
под шаблон

```
^[0-9]{13}-[a-z0-9][a-z0-9._-]{0,63}-(started|success|failure|rolled_back|rollback|published)\.json$
```

`.tmp` под него не подходит ни при каком раскладе, поэтому недописанный файл
невидим для читателя, даже если `rename` где-то заменят на `cp`.

`fsync` до `rename` — не педантизм: без него после выключения питания в
каталоге останется имя, за которым нули. Сообщение о выкатке стоит одного
`fsync` на выкатку.

## 4. Поля

Тип «строка» везде значит UTF-8 без управляющих символов (см. §8 и §9).

| Поле | Тип | Обязательность | Что это |
|---|---|---|---|
| `v` | число | всегда | версия схемы, сейчас `1` |
| `id` | строка, 64 hex | всегда | ключ дедупликации, см. §5 |
| `kind` | перечисление | всегда | `started`, `success`, `failure`, `rolled_back`, `rollback`, `published` |
| `app` | строка | всегда | id цели: `snakes`, `metro`, `status-bot`, … |
| `at` | RFC3339 UTC | всегда | момент события, всегда с `Z` |
| `source` | перечисление | всегда | `ci` или `local` |
| `group` | строка, 64 hex | всегда | прогон, к которому относится событие, см. §6 |
| `groupSeq` | целое ≥ 1 | всегда | порядковый номер события внутри группы, см. §6 |
| `version` | строка | см. таблицу ниже | версия, которую выкатывали |
| `previous` | строка | нет | что было на проде до этого |
| `changelog` | массив строк | нет | пункты изменений, простой текст |
| `commitURL` | строка | нет | адрес коммита этой версии |
| `runURL` | строка | нет | адрес прогона; только при `source: ci` |
| `stage` | перечисление | см. таблицу | где остановилось, §7 |
| `reason` | перечисление | см. таблицу | почему откатились, §7 |

Ключей, которых нет в таблице, в событии быть не должно. Читатель на лишний
ключ не падает (иначе добавление поля означало бы одновременное обновление обеих
сторон), но и не пересказывает его в чат.

Необязательное поле **отсутствует**, а не приходит пустым. `"previous": ""` —
это «предыдущей версии нет», а `"changelog": []` — «изменений нет», и оба
утверждения ложны, когда на самом деле значение просто не удалось вычислить.
Пустой строкой и пустым массивом сериализовать нечего: ключ не пишется вовсе.

### Обязательность по видам

| `kind` | `version` | `previous` | `stage` | `reason` | Смысл |
|---|---|---|---|---|---|
| `started` | нет | нет | запрещён | запрещён | выкатка началась |
| `success` | да | нет | запрещён | запрещён | выкатилось и проверилось |
| `failure` | нет | нет | **да** | запрещён | не выкатилось, прод не тронут или откачен своими силами |
| `rolled_back` | да | нет | **да** | **да** | автооткат внутри `release.sh` |
| `rollback` | **да** | нет | запрещён | `manual` | ручной откат `rollback.sh`; `version` — релиз, НА который откатились |
| `published` | да | нет | запрещён | запрещён | опубликован файл (`publish-file.sh`) |

`version` у `failure` необязателен намеренно: провал на гейтах случается до
того, как версия вообще посчитана, и требовать её значило бы либо врать
заглушкой, либо молчать о самом раннем классе провалов.

`started` заводится сразу, но в чат по умолчанию не идёт: он нужен детектору
аномалий («выкатка началась и не кончилась») и метрике времени выкатки. Правило
одно и записано здесь, чтобы каждая сторона не решала его заново.

### `app`

`^[a-z0-9][a-z0-9._-]{0,63}$`. Тот же набор, что у имени каталога релиза
(`assert_path_component` в `server/lib.sh`), потому что `app` попадает в **имя
файла**. Никаких `/`, никаких `..`, никаких пробелов: имя файла собирается
конкатенацией, и это единственное, что стоит между чужой строкой и записью в
соседний каталог.

### `version`, `previous`

До 128 байт, тот же набор символов, что у `app`, плюс `+`. Формы, которые
бывают в хозяйстве: `release-20260805-101502-1a2b3c4` (пайплайн),
`manual-20260805-101502-1a2b3c4` (с машины), собственная версия проекта у целей
с `VERSION_CMD` (`bin/deploy`, режим публикации файла).

### `changelog`

Массив **простого текста**, не разметки. До 20 пунктов, каждый — до 120
символов и не длиннее 512 байт.

Разметку не возит никто: `bin/changelog` отдаёт готовый кусок HTML с
`<b>Изменения</b>`, маркерами `•`, экранированными `&lt;` и, если передана база,
тегами `<a href>`. В событие это уезжать не должно — иначе бот получает
недоверенный HTML, который ему нельзя ни экранировать (сломается разметка), ни
не экранировать (это дыра). Поэтому producer вызывает генератор и приводит
результат к тексту:

1. `changelog --no-header --max 20 --width 120` — без шапки, с пределами;
2. выбросить хвост `…и ещё N коммитов` (число пунктов в событии ограничено
   своим пределом, и два разных «обрезано» в одной строке читателю не нужны);
3. снять префикс `• `;
4. убрать теги `<a href="…">#21</a>`, оставив видимый текст `#21`;
5. развернуть `&amp;`, `&lt;`, `&gt;` обратно в `&`, `<`, `>`.

Разметку обратно навешивает бот — один раз, в одном месте, из уже
экранированного текста (`format.go`, `formatChangelog`). Сто двадцать символов
на пункт — потолок темы коммита из `CLAUDE.md`; двадцать пунктов — предел
события, а не предел сообщения: сообщение бот при необходимости делит
(`splitMessage`).

### Диапазон `changelog` — от живого прода, а не от диапазона пуша

Список изменений в событии покрывает отрезок **«коммит, который прямо сейчас
работает на проде» → «коммит выкатываемого релиза»**. Не `github.event.before`,
не «коммиты этого пуша».

Причина не в красоте отсчёта, а в том, что прогоны пропадают не по нашей воле.
GitHub держит в очереди на группу `concurrency` ровно **одну** ожидающую задачу:
катится A, ждёт B, приходит C — прогон B **отменяется**, и `cancel-in-progress:
false` этого не меняет, такой настройки нет вовсе. Выкатки B не будет.

Дальше решает только выбор диапазона:

* от диапазона пуша — следующий релиз считает «от C», и коммиты B не объявит
  **никогда**: они не попадут ни в чат, ни в `version.json`, ни в это событие.
  Каждый релиз рассказывает про свой отрезок, и пропущенный отрезок не подберёт
  никто;
* от живого прода — пропущенный прогон не теряет ничего. Прод остался на A,
  значит следующая выкатка объявит и свои коммиты, и коммиты B. Свойство
  самовосстанавливающееся, а не однократное.

Поэтому «список ровно этого пуша» — не то свойство, которое стоит защищать.
Ценность события в том, что **ни одно изменение не исчезает из ленты**, а
совпадение с границами пуша — лишь один из способов этого добиться, и способ,
который ломается на первом же вытесненном прогоне. Читатель ленты не знает про
прогоны и очереди; он знает, что видел, и что не видел.

Цена честная: если между двумя выкатками прод стоял через откат, диапазон
«прод → HEAD» может повторить уже объявленные пункты. Повтор виден и безобиден,
пропажа не видна и необратима.

Начало диапазона берётся из `version.json` цели (`VERSION_URL` в её описании):
поле `commit`, а при его отсутствии — `version`, из которой хвостовой sha
достаёт сам генератор. Коммит прода может лежать глубже `fetch-depth: 50`, с
которым выкатка делает checkout, — тогда генератор доуглубляет клон сам
(`bin/changelog --deepen`).

Запасной путь остался прежним (`github.event.before`, затем тег, затем последние
N коммитов), но он **громкий**: прод не ответил, поля нет, коммит недостижим
после форс-пуша — прогон получает `::warning::` с прямым текстом о том, что
коммиты вытесненного прогона в ленту не попадут. Тихий откат на худшее поведение
здесь запрещён: именно молчание и превращает такую дыру в многолетнюю.

### `commitURL`, `runURL`

До 300 байт. Принимается **только** `https://` и только известный хост:

```
github.com
```

Проверяет обе стороны: писатель — потому что не должен собирать событие с
мусором, читатель — потому что событие приезжает файлом и подделать его может
любой, кто пишет в каталог. `link()` в боте экранирует `href`, но схему сегодня
не смотрит; событие обязано доехать до него уже проверенным, иначе выкатка
кладёт в чат ссылку `javascript:` или фишинговый адрес от имени бота, которому
владелец доверяет по определению.

Адрес, не прошедший проверку, — не повод отбросить событие: поле просто
выбрасывается, и версия в сообщении остаётся обычным текстом (ровно так же, как
при отсутствии `commitURL` сегодня).

`runURL` при `source: local` запрещён: прогона нет, и ссылка «на прогон» с
машины разработчика может вести только куда-то не туда.

### Чего в событии нет

**Заголовка цели и её адреса.** Бот берёт их из `summary.json`, где уже живёт
реестр проектов. Положив их в событие, мы завели бы вторую правду о том, как
называется проект, и первое же переименование развело бы чат и страницу. Если
`app` в реестре не нашёлся, бот показывает `app` как есть и без ссылки — это
видно и чинится, в отличие от тихо разъехавшихся названий.

**Имени хоста и имени пользователя.** Они участвуют в вычислении `id` (§5) и
`group` (§6), но в сам файл не попадают: событие уезжает в чат и кормит
публичную страницу, а внутренние имена — это ровно то, чего там быть не должно.
Обе величины — хеши, прообраз по ним не восстанавливается.

**Числа целей в прогоне.** Ни `groupTotal`, ни «цель 3 из 6»: писатель первого
события не знает, сколько целей вообще доедет до выкатки (прогон может упасть
на второй), а число, посчитанное заранее и не совпавшее с итогом, хуже
отсутствующего. Сообщение группы растёт по мере готовности целей, см. §6.

**Сырого вывода лога.** Никогда и ни в каком поле. Причина — §7.

## 5. `id` и дедупликация

`id` — 64 строчных hex-символа, всегда sha256 от канонической строки:

```
CI:      sha256("<repo>|<run_id>|<attempt>|<app>|<kind>")
локально: sha256("<unix-ms>|<host>|<pid>|<app>|<kind>")
```

Разделитель — `|`, перевода строки в конце нет, кодировка UTF-8, вывод —
строчный hex.

* `<repo>` — `github.repository`, то есть `tr0llex/snakes`;
* `<run_id>`, `<attempt>` — `github.run_id` и `github.run_attempt`;
* `<unix-ms>` — тот же миллисекундный момент, что и в имени файла (после
  разрешения столкновения, §2);
* `<host>` — `hostname` машины, где событие родилось;
* `<pid>` — pid процесса-писателя.

**Форма `id` одна на оба случая — это решение, а не совпадение.** Можно было
возить «сырую» строку и разбирать её на стороне читателя, но тогда у читателя
появились бы две формы `id`, два регулярных выражения и вопрос «что делать с
третьей». Здесь всё проще: `^[0-9a-f]{64}$`, одна проверка, и внутрь никто не
заглядывает. Заодно из события исчезает имя хоста — оно осталось в прообразе.

**Зачем дедупликация.** Доставка повторяется по построению: транспорт делает
три попытки, повтор прогона в GitHub Actions — одна кнопка, а `if: always()`
срабатывает в каждой попытке. Плюс сам бот перечитывает журнал после
перезапуска (§10). Два одинаковых сообщения о выкатке в чате хуже одного: чат —
это летопись прода, и по ней считают, сколько раз катились сегодня. Пропущенное
событие видно сразу (о выкатке не сказали), а лишнее — не видно вовсе, оно
просто врёт.

Поэтому в `id` для CI входят `run_id` и `attempt`: **повтор прогона — это новая
выкатка** и о ней надо сказать, а повтор доставки внутри одного прогона — нет.
Для локальной выкатки ту же роль играет `pid`: два запуска `dk deploy` — два
процесса, а три попытки одного `scp` — один.

`app` и `kind` в прообразе — потому что один прогон выкатывает несколько целей и
порождает несколько событий на цель (`started`, потом `success`).

## 6. Группировка по прогону

**Один пуш выкатывает несколько целей.** У `double-or-die` их две (`dev` и
`game`, последовательно, один прогон), у `chillhub` — шесть, у
`status.samoy.love` — три. Коммит при этом один, и список изменений у всех целей
**один и тот же**: он считается по истории репозитория, а не по цели.

Шесть сообщений с одинаковым блоком «Изменения» — это способ перестать читать
чат. Именно так лента релизов и умирает: не от одного лишнего сообщения, а от
того, что полезное в ней тонет в повторах, и её перестают открывать вовсе.

Поэтому событие несёт два поля группы.

### `group`

```
CI:       sha256("<repo>|<run_id>|<run_attempt>")
локально: sha256("<unix-ms старта>|<host>|<pid>")
```

Те же правила, что у `id` (§5): разделитель `|`, UTF-8, строчный hex,
`^[0-9a-f]{64}$` — одна проверка на оба случая, внутрь никто не заглядывает.

**Прогон в CI** — это `run_id` вместе с `run_attempt`: повторный запуск прогона
одной кнопкой — новая выкатка, новая группа и новое сообщение. Так же, как в
`id`, и по той же причине.

**Локально группа — один вызов `dk deploy`**, включая `dk deploy --all`,
который катит все цели проекта подряд. Одна команда владельца — одно сообщение
в чате. Отсюда и прообраз: `pid` постоянен на весь вызов, а `<unix-ms старта>` —
момент **запуска команды**, а не момент события. Это единственное место, где
миллисекунды в прообразе не те же, что в имени файла: имя нумерует события,
группа именует вызов.

Заметно, что для CI прообраз `id` — это ровно прообраз `group` плюс
`|<app>|<kind>`. Совпадение полезное, но опираться на него нельзя: локально оно
не выполняется, и читатель обязан брать `group` из поля, а не выводить его из
`id`.

### `groupSeq`

Целое, начинается с `1`, растёт на единицу с каждым событием группы. Считает
писатель — под тем же `flock`, которым разрешается столкновение имён (§2), по
счётчику `<каталог>/.groups/<group>`. Точка в начале имени выводит счётчики
из-под шаблона имени события (§3), поэтому для читателя их не существует;
чистятся они тем же правилом четырнадцати суток, что и события (§11).

**`groupSeq` — подсказка, а не власть.** Решение «новое сообщение или правка»
бот принимает по своей записи о группе (§10), а не по номеру: счётчик может
потеряться вместе с переустановкой сервера, а события могут доехать не по
порядку. Номер нужен для двух вещей: разобрать порядок в журнале задним числом
и заметить дыру в доставке метрикой.

### Правило бота: первое сообщение, дальше правки

1. Пришло событие с **незнакомой** `group` — бот **немедленно** отправляет новое
   сообщение и запоминает `message_id` рядом с `group`.
2. Пришло событие с **известной** `group` — бот **не отправляет ничего нового**,
   а перерисовывает уже отправленное сообщение (`Telegram.Edit`, для длинных —
   `EditLong`; `bot/telegram.go:376,405`, бот это умеет с самого начала —
   так работает кнопка «Обновить»).

Сообщение группы устроено так: шапка прогона, **список изменений — один раз**, и
строки целей с исходом каждой:

```
🚀 chillhub · release-20260805-130115-1a2b3c4

  сайт          выкачен
  лаунчер       выкачен
  админка       откачена — не прошёл healthcheck
  api           провалена на units
  бот           выкатывается…
  downloads     выкачен

Изменения
• Не выдавать недоставленное уведомление за успех
• Считать пропавший файл ошибкой обновления
```

Форма строк — дело форматтера, контракт задаёт только правило: одно сообщение
на прогон, изменения печатаются один раз, цели перечисляются с исходом.

### Почему правка, а не ожидание конца прогона

Дождаться последней цели и отправить одно готовое сообщение — очевидный
соблазн, и он стоит слишком дорого. Прогон `chillhub` идёт минутами, а
`desktop-artifact` — десятками минут; всё это время в чате было бы пусто, и
самое ценное свойство события — **мгновенность** — оказалось бы принесено в
жертву аккуратности. Хуже того, «конец прогона» — величина, которой у писателя
нет: прогон, упавший на середине, не сообщает о себе ничего, и сообщение не
пришло бы вовсе.

Правка даёт и то, и другое: первая цель попадает в чат за секунду, остальные
дописываются в то же сообщение. Владелец видит выкатку с самого начала и в
конце имеет ровно одну карточку прогона вместо шести.

### Почему не дедупликация по списку изменений

Соблазн второй: «одинаковый changelog — значит одно и то же, показать один раз».
Так делать нельзя. **Две разные выкатки одной цели могут нести один и тот же
список**: повторный запуск прогона после починки инфраструктуры, выкатка того же
коммита в `dev` и в `game`, перевыкатка после отката. Схлопнув их, мы потеряли
бы настоящую выкатку — а потеря выкатки и есть то, ради чего вся эта работа
затевалась. `group` отвечает на вопрос «это один прогон?» точно; список
изменений — только похоже.

### Срок жизни группы

Бот помнит `message_id` группы **6 часов**. Это десятикратный запас к самому
долгому прогону хозяйства; за это время все цели любого репозитория успевают
объявить исход многократно.

Событие группы, пришедшее позже, — это **новое сообщение**, а не правка.
Причины две, и обе жёсткие:

* править сообщение недельной давности бессмысленно: его давно пролистали, и
  правка не поднимет его в чате — изменение окажется невидимым;
* Telegram править старые сообщения и не даст, а ошибка правки в отправителе
  превратилась бы в бесконечный повтор.

Такое событие обрабатывается как первое событие своей группы: уходит новым
сообщением, и запись о группе заводится заново — уже без исходов целей, о
которых говорилось сутки назад. Повтора при этом не будет: за «не показывали ли
мы это уже» отвечает `recentIds` (§10), и он живёт дольше группы намеренно.

Отсюда же правило на ошибку правки в пределах шести часов: если Telegram
ответил, что сообщения нет или его нельзя изменить (владелец удалил карточку
прогона), бот **отправляет новое сообщение** с текущим состоянием всей группы и
перепривязывает `message_id`. Молчание тут недопустимо: цель выкачена, а в чате
об этом не сказано.

Число групп в состоянии ограничено сотней: при переполнении выбрасывается самая
старая. Сотня прогонов за шесть часов — это уже аномалия, а не рабочий день.

## 7. `stage` и `reason` — закрытые перечисления

### `stage` — где остановилось

| Значение | Что происходило |
|---|---|
| `gates` | проверки до сборки: тесты, линтеры, проверка коммитов |
| `preflight` | сборка артефакта, проверка описания цели, версионный шлюз |
| `upload` | доставка артефакта на сервер |
| `switch` | распаковка, переключение `current`, reload nginx |
| `units` | установка юнитов systemd и перезапуск службы |
| `health` | HTTP-healthcheck и собственная проверка цели (`verify`) |
| `version` | сверка `/version.json` с тем, что выкатывали |
| `neighbours` | проверка соседних целей после переключения |

### `reason` — почему откатились

| Значение | Когда |
|---|---|
| `units_failed` | `install_units` не отработал |
| `nginx_failed` | `nginx -t` не прошёл или reload не отработал |
| `health_failed` | `wait_http` не дождался живого ответа |
| `verify_failed` | `verify` из артефакта вернул не ноль или не уложился в 120 с |
| `version_mismatch` | прод раздаёт не ту версию, которую выкатывали |
| `neighbours_failed` | `check_neighbours` уронил соседей |
| `manual` | откат запущен руками (`rollback.sh`) |

### Соответствие точкам `release.sh`

Перечисление `stage` закрыто и шире не станет, поэтому детали ложатся в
`reason`, а не в новые стадии:

| Точка отказа | `stage` | `reason` |
|---|---|---|
| `install_units "$NEW_DIR" \|\| rollback` | `units` | `units_failed` |
| `nginx -t` / `systemctl reload nginx` | `switch` | `nginx_failed` |
| `systemctl restart "$UNIT" \|\| rollback` | `units` | `units_failed` |
| `wait_http "$HEALTH"` | `health` | `health_failed` |
| `verify` из артефакта | `health` | `verify_failed` |
| `check_version` / расхождение симлинка | `version` | `version_mismatch` |
| `check_neighbours` | `neighbours` | `neighbours_failed` |
| версионный шлюз (`version_gate`, код 3) | `preflight` | — (это `failure`, не откат) |

### Почему это перечисления, а не текст

**Сырой вывод лога не попадает в событие никогда.** В логе выкатки бывают пути
на сервере, имена хостов, куски конфигурации, тела ответов сервисов и
содержимое переменных окружения; в логе `nginx -t` — полная раскладка
конфигурации. Событие уезжает в чат и потенциально на публичную страницу
`status.samoy.love`, и «показать причину подробнее» тут значит «опубликовать
кусок внутренностей сервера».

Перечисление снимает вопрос целиком: множество значений конечно, известно
заранее и не зависит от того, что напечатала упавшая команда. Читатель, увидев
незнакомое значение, показывает вид события без стадии — но событие не теряет.
Кому нужны подробности, идёт по `runURL` в прогон или в журнал на сервере, где
им и место.

## 8. Потолки

| Что | Предел | Почему |
|---|---|---|
| размер файла события | 8 КиБ | читатель делает `stat` до чтения и больший файл не открывает вовсе |
| `id`, `group` | ровно 64 байта | sha256 hex |
| `groupSeq` | целое, 1…10000 | больше десяти тысяч событий в одном прогоне не бывает |
| `app` | 64 байта | уезжает в имя файла |
| `version`, `previous` | 128 байт | |
| `at` | 32 байта | RFC3339 |
| `stage`, `reason`, `kind`, `source` | 24 байта | перечисления |
| `commitURL`, `runURL` | 300 байт | |
| пункт `changelog` | 120 символов и 512 байт | потолок темы коммита из `CLAUDE.md` |
| пунктов `changelog` | 20 | |
| событий в сутки на цель | 200 | |
| файлов в каталоге | 5000 | |
| размер каталога | 32 МиБ | |
| групп в `state.json` бота | 100 | §10 |
| целей в сообщении группы | 20 | больше в одном прогоне не выкатывает ни один репозиторий хозяйства |

Символы и байты считаются оба, и это не перестраховка: кириллическая буква —
один символ и два байта, и предел «120 символов» без байтового потолка
означал бы 480 байт на четырёхбайтовых символах.

**Превышение — отказ записи, а не обрезка.** Писатель, упёршийся в суточный
предел или в потолок каталога, событие не пишет, печатает `::error::` и
возвращает ненулевой код. Молча выбросить событие нельзя: тишина в чате
означает «не катились», и подменять ею «катились, но журнал переполнен» —
это ровно тот дефект, ради которого всё затевалось.

Потолок каталога — не про аккуратность. Журнал лежит на том же разделе, что и
данные агента; переполнение раздела убивает агента, а с ним всю статус-систему
целиком. Цикл, крутящий `dk deploy` в ошибке, не должен иметь возможности
положить наблюдение за продом.

**Суточный предел считается по календарным суткам UTC и по каждой цели
отдельно.** Двести событий на цель — это примерно сорок выкаток в день при пяти
событиях на выкатку: втрое больше самого шумного дня в истории хозяйства.

## 9. Что читатель обязан отвергнуть

Каталог событий пишет деплойный пользователь, и это тот же, кто и так может
выкатить прод (эскалации привилегий канал не даёт). Но читатель — бот с
токеном Telegram, и разбирать он обязан так, будто файл положил кто угодно.

1. **Имя не по шаблону** (§3) — файл не существует для читателя. Сюда попадают
   `.tmp`, `..`, имена со слэшем, всё лишнее.
2. **Не обычный файл** — открывать с `O_NOFOLLOW`. Симлинк на `/etc/shadow` в
   каталоге событий не должен превращаться в чтение `/etc/shadow` процессом
   бота.
3. **Размер больше 8 КиБ** — `stat` до открытия, файл не читается.
4. **Не разбирается как JSON, не тот `v`, не проходит проверку полей** —
   пропустить, посчитать в метрику, курсор сдвинуть. Испорченный файл не имеет
   права остановить журнал: иначе одна опечатка глушит уведомления навсегда.
5. **Управляющие символы и `U+202E`** в любом текстовом поле — вырезать.
   `U+202E` переворачивает направление текста и позволяет показать в чате не то,
   что написано; `CR`/`LF` в поле подделывают строки journald при логировании.
6. **Разбор без паники на любом входе.** Мусор — обычный вход, а не
   исключительный.

Ничего из перечисленного не должно роняться в `panic` и ничего не должно
останавливать обработку следующих файлов.

## 10. Поля в `state.json` бота

К существующим `offset`, `mutedUntil`, `items`, `versions` добавляются четыре.

```json
{
  "inboxCursor": "1785924102123-snakes-success.json",
  "outboxCursor": "1785924102123-snakes-success.json",
  "recentIds": {
    "d209f71003ade058bf845a91031f2cf424fe40567d446ecb689bfb15df32fa91": "2026-08-05T10:18:22Z"
  },
  "groups": {
    "760e4d55c197922abe742e60a367ad828fb1259b1a3da225a5bbb257d8242ad6": {
      "messageID": 4821,
      "at": "2026-08-05T10:01:42Z"
    }
  }
}
```

**`inboxCursor`** — имя последнего файла, принятого приёмником в очередь.
Приёмник берёт из каталога только имена, строго большие этого значения как
строки (§2), поэтому один проход по отсортированному списку решает и «что
нового», и «в каком порядке».

**`outboxCursor`** — имя последнего файла, по которому сообщение подтверждено
Telegram. Всегда не больше `inboxCursor`.

Курсора два, потому что очередь отправки живёт в памяти. Убитый бот теряет
всё, что принял, но не отправил; поэтому **на старте `inboxCursor` берётся
равным `outboxCursor`** и неотправленное перечитывается с диска. Ровно за этим
журнал и лежит на диске: он переживает и лежачего бота, и лежачий Telegram.

**`recentIds`** — множество недавних `id` со временем приёма. Живёт **14
суток** — ровно столько, сколько живёт сам файл события (§11). Правило простое:
пока файл может быть перечитан, его `id` обязан помниться, иначе после
перезапуска бот повторит в чат всё, что лежит в каталоге. Чистится при каждой
записи состояния — записей у бота и так достаточно, отдельный таймер тут лишний.

Предел размера: 200 событий в сутки на цель × 14 суток — это тысячи ключей по
64 байта, то есть сотни килобайт в худшем случае. `state.json` пишется через
временный файл и `rename` (`saveState`), поэтому размер влияет только на
скорость записи.

**`recentIds` пополняется вместе со сдвигом `outboxCursor`, то есть после
подтверждения Telegram, и в той же записи состояния.** Это осознанный выбор
между двумя рисками. Пометив `id` при приёме, мы получили бы потерю сообщения
при падении между приёмом и отправкой — а потерянная выкатка и есть то, что
чинится этим планом. Пометив после отправки, мы получаем редкий дубль: падение
ровно между ответом Telegram и записью состояния. Транзакции с чужим сервисом
не бывает, третьего варианта нет, и выбран тот, где отказ громкий.

Главная работа `recentIds` при этом другая и куда более частая: транспорт
повторяет доставку, и **два файла с разными именами могут нести один `id`**.
Отличить их можно только по `id` — курсор здесь не помогает никак.

**`groups`** — карта `group` → сообщение прогона: `messageID` в чате и `at`
времени отправки первого сообщения группы. Это и есть та память, на которой
держится правило §6: известная `group` — правка `messageID`, незнакомая — новое
сообщение.

Запись появляется **после подтверждения Telegram** — раньше `messageID` попросту
неоткуда взять, — и вместе с ней в состояние ложится всё, что нужно, чтобы
перерисовать сообщение целиком: исходы уже объявленных целей и общий для
прогона список изменений. Держать это только в памяти нельзя: перезапуск бота
посреди прогона `chillhub` превратил бы правку в затирание пяти строк одной.

Живёт запись **6 часов** (§6) и не больше ста записей на состояние; и то и
другое чистится в той же записи состояния, что и `recentIds`. Обратите
внимание, что сроки у `groups` и `recentIds` РАЗНЫЕ и это намеренно: `recentIds`
отвечает на вопрос «не показывали ли мы это уже» и обязан жить столько же,
сколько файл события (14 суток), а `groups` — на вопрос «есть ли ещё смысл
править то сообщение», и ответ на него перестаёт быть «да» через несколько
часов.

## 11. Права, владение и чистка

```
/var/lib/deploy-kit/events   deploy:deploy-events   drwxr-s--T  (3750)
/var/lib/deploy-kit/events/* deploy:deploy-events   -rw-r-----  (0640)
```

**Пишет деплойный пользователь** — тот самый `DEPLOY_USER`, которым идёт
выкатка. Других писателей нет.

**Читатели — строго только на чтение.** Бот (`samoylove-bot`) и агент
(`status`) входят в группу `deploy-events` и получают на каталоге `r-x`, на
файлах `r--`. В юните бота это закрепляется отдельно:

```
ReadOnlyPaths=/var/lib/deploy-kit/events
```

Читатель, который умеет удалять обработанное, — это читатель, который умеет
удалить необработанное. У бота уже есть токен Telegram и `ProtectSystem=strict`;
права на журнал выкаток он получать не должен, а курсор решает ту же задачу
лучше: он переживает перезапуск и не портит данные для второго читателя.

**Sticky bit (`+t`)** стоит, хотя писатель сегодня один: он запрещает удалять и
переименовывать чужие файлы тем, кто в каталог всё-таки пишет. Стоит копейку,
снимает целый класс сюрпризов при появлении второго писателя (например,
Alertmanager, если он станет источником событий).

**Чистит писатель.** Перед записью нового события он удаляет из каталога файлы
старше **14 суток** по имени (первые 13 цифр), а не по `mtime`: `mtime`
переживает `cp -a` и меняется при `touch`, а имя — это то же самое время,
которое видит курсор.

Почему 14 суток. Столько же живут `recentIds` (§10), и обе величины обязаны
совпадать: файл, который ещё лежит, но чей `id` уже забыт, приедет в чат
повторно. Две недели — это отпуск владельца, лежачий бот и любой разумный
разбор инцидента задним числом; на 200 событиях в сутки на цель это заведомо
внутри потолка каталога.

Удаление — единственная операция чистки. Никаких архивов и ротации: история
релизов живёт в `releases.json`, который агент собирает из журнала, и хранить
её дважды незачем.

## 12. Как событие становится сообщением

**Форма сообщения о релизе не меняется.** `kind: success` у цели, которая в
своём прогоне одна, превращается ровно в то же сообщение, что бот шлёт сегодня
по разнице версий (`KindRelease` в `format.go`): заголовок с ссылкой, версия,
«была …», время, список изменений последним блоком. Меняется только то, откуда
бот узнал о релизе.

Прогон из нескольких целей собирается в одно сообщение по правилам §6 — и это
единственный случай, когда читатель увидит другую форму. Одноцелевой прогон
(таких в хозяйстве большинство) по этим же правилам даёт ровно прежнюю карточку:
группа из одного события — это первое событие группы, то есть обычная отправка.

| Поле события | Поле `Event` бота |
|---|---|
| `app` | `Key`, а `Title`/`URL`/`Project` — из реестра `summary.json` |
| `version` | `Version` |
| `previous` | `Previous` |
| `at` | `At` |
| `changelog` | `Changelog` |
| `commitURL` | `CommitURL` |
| `group` | ключ записи в `State.Groups`: отправить или править (§6, §10) |
| `groupSeq` | в сообщение не попадает: номер служебный (§6) |

Новые виды сообщений (`failure` со стадией и ссылкой на прогон, `rolled_back` с
причиной, `rollback`) добавляются рядом, старый вид остаётся как есть. Ленту
релизов читают годами; переписать её форму заодно с транспортом — значит
сломать единственное, что в этой работе и так работало.

`started` и `published` в чат по умолчанию не идут: первый — служебный (§4),
второй показывается по правилам цели.

Событие обновляет `State.Versions` — иначе следующее наблюдение той же версии
объявит релиз второй раз. Пока старый путь жив, это и есть то, что защищает от
дублей на переходе.

## 13. Образцы

Лежат рядом и подключены golden-файлами в тестах обеих сторон.

* `docs/events/example-success.json` — выкатка из пайплайна; `groupSeq: 2`,
  потому что первым в группе был `started` этой же цели;
* `docs/events/example-failure.json` — провал на гейтах, версии ещё нет;
  `groupSeq: 1` — гейты стерегут весь прогон, до целей дело не дошло, и это
  первое (оно же единственное) событие группы;
* `docs/events/example-rolled-back.json` — автооткат по мёртвому healthcheck,
  выкатка с машины; группа локальная, `groupSeq: 2` после `started`.

`id` и `group` в образцах — настоящие sha256 от прообразов §5 и §6, и тест
обязан их пересчитывать, а не сверять с константой в своём коде:

```
id   tr0llex/snakes|16542330981|1|snakes|success
       → d209f71003ade058bf845a91031f2cf424fe40567d446ecb689bfb15df32fa91
group  tr0llex/snakes|16542330981|1
       → 760e4d55c197922abe742e60a367ad828fb1259b1a3da225a5bbb257d8242ad6

id   tr0llex/chillhub|16542331744|2|chillhub-site|failure
       → 6de00661e76009ac12a18c7f7a395452e790286cb6756bc7c1be1607c250867d
group  tr0llex/chillhub|16542331744|2
       → ae40809c132b755feaa6a97e123d092ec6a5c3888c8900ae9fd33e4e934dbb48

id   1785925215123|samoy-love|31415|metro|rolled_back
       → bd50fb8291b509604f57f43e1183998e64912402952043c103a32fabb0dd1fe4
group  1785925180000|samoy-love|31415
       → 593aeadec622fe57a0cca371105341c9dfeaafb5282fdff081d1d09d1c5b6c11
```

В третьем образце миллисекунды у `id` и у `group` разные — и это не опечатка, а
ровно то правило §6, ради которого стоит держать локальный образец: `id` считан
от момента события (10:20:15.123), `group` — от момента запуска `dk deploy`
(10:19:40.000). Тест, который подставит в оба прообраза одно число, сойдётся с
образцом только по случайности.

Проверить руками:

```bash
printf '%s' 'tr0llex/snakes|16542330981|1|snakes|success' | sha256sum
```

Имена файлов, под которыми эти образцы легли бы в журнал:

```
1785924102123-snakes-success.json
1785923700456-chillhub-site-failure.json
1785925215123-metro-rolled_back.json
```
